# Этап 1: прототип «Поставки и экономика рейсов» — спецификация

Дата: 11 ноября 2026 · Основание: PRD версии 0.1 от 10 ноября 2026 · Статус: на согласовании

## 1. Цель и границы

Рабочий веб-сервис, в котором один сквозной сценарий проходит от загрузки заказа до финансового закрытия рейса. Основа настоящая: база данных, организации, роли, доступ водителя по ссылке. Данные демонстрационные и обезличенные: пилотной компании пока нет, поэтому форматы импорта настраиваются сопоставлением колонок.

### Входит

1. Организация, пользователи, роли.
2. Справочники: точки, машины, водители, контрагенты.
3. Импорт заказов из XLSX и CSV.
4. Сборка рейса из заказов, деление заказа между рейсами.
5. Расчёт грузовых вариантов маршрута через 2ГИС, сравнение вариантов и исполнителей.
6. Назначение своей машины или подрядчика, версии плана.
7. Мобильная ссылка водителя.
8. Ручной факт рейса и приёмка по строкам, задачи по отклонениям.
9. Расходы, начисления, счета, оплаты, план-факт, распределение стоимости доставки.
10. Финансовое закрытие рейса.
11. Экран «Разобрать», журнал изменений, экспорт XLSX и CSV.

### Не входит

| Что | Когда по PRD | Что заменяет в этапе 1 |
|---|---|---|
| Импорт из 1С, ATI.SU | Этап 2 | Файл заказов; ставка подрядчика вручную |
| GPS, банк, EDI, оператор ЭПД, уведомления | Этап 3 | Ручной факт, ручные платежи, ручная приёмка, ручной статус документа |
| Другие биржи, автоматическое распределение заказов, аналитика подрядчиков | Этап 4 | — |
| Запрос ставки по ссылке | После пилота | Ставка из звонка или переписки вводится вручную |
| Геокодирование адресов | Не запланировано | Координаты точки задаются кликом по карте или вручную |
| Импорт факта рейса, расходов и банковской выписки из файла | Этапы 2–3 | Ручной ввод; механизм импорта общий и расширяется типом файла |
| Дашборды руководителя | Этап 4 | Доступ на чтение и экспорт |
| Режим перевозчика (прибыль по клиентам и машинам) | После пилота | Режим поставщика; выручка за перевозку необязательна |

## 3. Решения по ограничениям 2ГИС

1. **Сырой ответ и геометрия не сохраняются.** Линия маршрута существует в памяти сервера и в браузере только на время сравнения вариантов.
2. **В версию плана записываются расстояние, время в пути, ETA и источник.** Это значения, которые логист подтверждает как план. Запись помечена как требующая подтверждения у 2ГИС. Настройка `ROUTE_METRICS_STORAGE` со значениями `plan` и `none` позволяет отключить запись: при `none` расчёт 2ГИС используется только для сравнения на экране, а в план попадают лишь значения, которые логист ввёл вручную.
3. **Экспорт значений из 2ГИС выключен по умолчанию.** Настройка `EXPORT_PROVIDER_METRICS=false` оставляет в выгрузке колонки расстояния и времени пустыми, если источник — 2ГИС.
4. **Тестовые данные адаптера синтетические.** Они написаны вручную по форме из документации. Запись живых ответов в репозиторий запрещена.
5. **Живой запрос уходит только по явному действию логиста.** Автотесты и разработка работают в режиме синтетического провайдера.
6. **Счётчик лимита.** Каждый успешный живой запрос учитывается; на экране видно «использовано N из 1 000» и дата окончания действия ключа.
7. **Карта на экране — OpenStreetMap через Leaflet.** Ключ 2ГИС в браузер не попадает. Адрес тайлов задаётся настройкой. Для коммерческой эксплуатации источник тайлов заменяется.
8. **Атрибуция.** Рядом с любыми значениями из 2ГИС стоит надпись «2ГИС» со ссылкой.

## 4. Архитектура

### 4.1. Стек

| Слой | Выбор | Причина |
|---|---|---|
| Приложение | Next.js (App Router), TypeScript, React | Один язык и один сервис; серверные обработчики держат ключ вне браузера |

| Карта | Leaflet | Не требует ключа |
| Файлы | exceljs для XLSX, csv-parse и csv-stringify для CSV | Чтение и запись без внешних сервисов |
| Тесты | Vitest; Playwright для сквозного сценария | — |
| Запуск | Docker Compose: приложение и PostgreSQL | Одна команда; размещение на VPS в РФ закрывает требование локализации персональных данных |

Авторизация собственная: адрес почты и пароль, хеш через `scrypt` из стандартной библиотеки Node.js, сессии в таблице базы, cookie с флагами `HttpOnly`, `Secure`, `SameSite=Lax`.

### 4.2. Модули

```
src/
  domain/      расчёты без ввода-вывода: деньги, распределение заказа,
               статусы рейса, ETA и окно, оценка затрат, план-факт,
               распределение стоимости, сверка оплат, проверка полноты
  server/
    db/        схема, миграции, репозитории с обязательной организацией
    auth/      сессии, роли, ссылки водителя
    routing/   интерфейс провайдера, 2ГИС, синтетический провайдер, счётчик
    import/    разбор файла, сопоставление, проверка, очередь заданий
    export/    выгрузки XLSX и CSV
    services/  сценарии: заказы, рейсы, план, исполнение, приёмка,
               деньги, задачи, журнал
  app/         страницы и обработчики Next.js; /d/[token] — ссылка водителя
```

Правила зависимостей:

- `domain` не импортирует ничего из `server` и `app`.
- `app` обращается к данным только через `services`.
- `services` получают `OrgContext` и не принимают идентификатор организации из запроса клиента.

### 4.3. Изоляция организаций

- У каждой таблицы с данными клиента есть `org_id`.
- `OrgContext` создаётся только из сессии или из ссылки водителя.
- Репозитории принимают `OrgContext` первым аргументом и добавляют условие по организации в каждый запрос.
- Интеграционный тест создаёт две организации и проверяет, что каждый сценарий чтения и записи второй организации не видит и не меняет данные первой.

Row Level Security в PostgreSQL в этап 1 не входит.

## 5. Модель данных

Деньги хранятся целыми копейками. У каждой суммы есть валюта (в этапе 1 только RUB), признак «с НДС» и ставка НДС. Расчёты ведутся на базе без НДС; ставка по умолчанию — настройка организации, начальное значение 22 %.

Время хранится в UTC. У точки есть часовой пояс; окна и ETA показываются во времени точки.

## 6. Маршрутизация

### 6.1. Интерфейс провайдера

```ts
interface RoutingProvider {
  buildRoutes(request: RouteRequest): Promise<RouteResult>;
}

type RouteRequest = {
  points: { lat: number; lon: number }[];   // от 2 до 10
  departureAt: Date;
  truck: TruckProfile | null;
  avoid: ("toll_road" | "dirt_road" | "ferry")[];
  alternatives: number;
};

type RouteResult =
  | { ok: true; variants: RouteVariant[]; profileComplete: boolean }
  | { ok: false; reason: RouteFailure; message: string };

type RouteFailure =
  | "no_key" | "quota" | "key_rejected" | "timeout" | "unavailable"
  | "not_found" | "points_too_far" | "point_off_road" | "bad_request";
```

`RouteVariant` содержит идентификатор, расстояние, время в пути, время до каждой остановки, признак «время до остановок оценено» и геометрию для показа.

### 6.2. Провайдер 2ГИС

- Запрос: `POST https://routing.api.2gis.com/routing/7.0.0/global?key=…`.
- Тело: `points` с `type: "stop"`, `transport: "truck"`, `output: "detailed"`, `locale: "ru"`, `alternative`, `filters`, `params.truck`.
- Поля `params.truck`: `max_perm_mass`, `mass`, `axle_load` (тонны), `height`, `width`, `length` (метры), `dangerous_cargo`, `explosive_cargo`, `pass_zone_pass_ids`.
- Выезд позже текущего момента: `traffic_mode: "statistics"` и `utc`. Выезд сейчас: `traffic_mode: "jam"`.
- Незаполненные поля профиля не передаются; `profileComplete` становится `false`, на экране стоит пометка «профиль неполный».
- Таймаут 10 секунд. Автоматических повторов нет: повтор запускает логист.
- Соответствие статусов ответа причинам отказа:

| Ответ 2ГИС | Причина | Текст для пользователя |
|---|---|---|
| `ROUTE_NOT_FOUND`, `ROUTE_DOES_NOT_EXISTS` | `not_found` | Маршрут между точками не строится |
| `ATTRACT_FAIL` | `point_off_road` | Точка дальше 10 км от дороги |
| `POINT_EXCLUDED` | `bad_request` | Точка попала в исключённую область |
| `FAIL`, HTTP 5xx | `unavailable` | 2ГИС не ответил, повторите позже |
| HTTP 401, 403 | `key_rejected` | Ключ отклонён или истёк |
| HTTP 429 или исчерпан счётчик | `quota` | Лимит запросов исчерпан |
| Превышение времени ожидания | `timeout` | 2ГИС не ответил за 10 секунд |

Точные коды ошибок для превышения 50 км и лимита демо-ключа в документации не описаны. Они сопоставляются при первой проверке живым ключом.

### 6.3. Режимы

- `ROUTING_MODE=synthetic` — по умолчанию. Варианты считаются по расстоянию по прямой с коэффициентом и средней скоростью. На экране стоит пометка «демо-расчёт, не 2ГИС».
- `ROUTING_MODE=live` — запросы в 2ГИС; требует `TWOGIS_API_KEY`. Без ключа возвращается `no_key`.

Перед живым запросом сервис проверяет расстояние по прямой между соседними точками. Если оно больше 50 км, логист видит предупреждение о вероятном отказе на демо-ключе и решает, отправлять ли запрос.

Вариант без платных дорог — отдельный запрос с фильтром `toll_road` по кнопке; он расходует ещё одну единицу лимита.

### 6.4. ETA и окно

- ETA остановки = время выезда + время в пути до неё + время обслуживания на предыдущих остановках + ожидание открытия окна.
- Время до промежуточных остановок берётся из ответа, если он его содержит. Иначе общее время делится между участками пропорционально расстоянию по прямой, и ETA помечается как оценка.
- Состояние по окну: «успевает» — ETA раньше конца окна минус запас; «риск» — в пределах запаса; «опоздание» — позже конца окна. Запас — настройка организации, начальное значение 15 минут.
- Прибытие раньше начала окна добавляет ожидание и сдвигает следующие остановки.

### 6.5. Ручная оценка

Если маршрут недоступен, логист вводит расстояние и время в пути. Вариант получает источник «ручная оценка» и отличается на экране и в экспорте.

### 6.6. Передача водителю

Ссылка водителя открывает точки в Яндекс Картах и Яндекс Навигаторе. Формат ссылок сверяется с документацией Яндекса при реализации. На странице сказано, что Яндекс может построить другой путь, а грузовой профиль водитель проверяет в приложении.

## 7. Оценка затрат и сравнение исполнителей

**Своя машина:**

- топливо = расстояние × норма расхода ÷ 100 × цена топлива;
- водитель = время рейса × стоимость часа;
- платные дороги — ввод логиста;
- прочее — ввод логиста.

Платные дороги имеют три состояния: «неизвестно», сумма, «платных участков нет». Вариант, построенный с фильтром `toll_road`, получает третье состояние автоматически. При состоянии «неизвестно» итог помечается как неполный.

**Подрядчик:** согласованная ставка, приведённая к базе без НДС, плюс ожидаемый простой по условиям предложения.

Каждая оценка показывает допущения: цену топлива, норму, стоимость часа, источник расстояния.

В очереди сравнения каждая строка — пара «маршрут и исполнитель» с ETA, состоянием по окну, оценкой затрат и причиной, по которой вариант не проходит. Найденный кандидат, полученная ставка и подтверждённое назначение — три разных состояния `carrier_offer`.

## 8. Рейс

### 8.1. Статусы

| Переход | Условие |
|---|---|
| черновик → запланирован | Есть остановки с грузом и текущая версия плана |
| запланирован → назначен | Своя машина: указаны машина и водитель. Подрядчик: предложение подтверждено |
| назначен → в работе | Первое событие исполнения |
| в работе → выполнен | По каждой остановке есть фактическое время или отметка «не состоялась» с причиной |
| выполнен → финансово закрыт | Проверка полноты пройдена либо есть решение с причиной |
| любой до «выполнен» → отменён | Указана причина |

Статусы заказов, приёмки, документов и оплаты ведутся независимо.

### 8.2. Перепланирование

Изменение маршрута, времени или исполнителя создаёт новую версию плана с причиной. Прежние версии не меняются. Смена исполнителя возвращает рейс в статус «запланирован».

### 8.3. Распределение заказа

- Строка заказа распределяется между рейсами количеством.
- Сумма распределений по строке не превышает количество в заказе; проверка стоит на уровне сервиса и базы.
- Остаток строки виден в очереди заказов.

### 8.4. Приёмка

- По каждой строке груза фиксируется: принято, отклонено, возвращено, код причины, подтверждение.
- Повторная приёмка создаёт новую версию; прежняя сохраняется.
- Принято меньше отгруженного — создаётся задача с ответственным и сроком, остаток и причина сохраняются.
- Приёмка не меняет заявленное количество в заказе.

### 8.5. Проверка полноты для финансового закрытия

1. По всему грузу есть приёмка.
2. Есть фактический пробег либо отметка «неизвестен».
3. По каждой плановой статье расходов есть факт либо отметка «не было».
4. Нет расходов со статусом «не проверен».
5. Нет согласованных доплат без счёта.
6. Нет открытых задач по рейсу.

Финансы или администратор могут закрыть рейс при невыполненных пунктах, указав причину. Причина и список невыполненных пунктов попадают в журнал.

## 9. Экономика и сверка

- **Результат рейса** считается только из начислений и расходов. Оплаты на него не влияют.
- **Задолженность** = выставлено по счетам − распределённые оплаты. Показывается отдельно от результата.
- **План и факт.** Плановые строки берутся из текущей версии плана на момент назначения. Отклонение раскладывается по статьям.
- **Неизвестные значения** помечаются и не считаются нулём: итог с неизвестной статьёй показывается как неполный.
- **Топливо.** Заправка — это покупка. Расход топлива вводится как оценка по норме и фактическому пробегу, с пометкой «оценка».
- **Распределение стоимости доставки по заказам.** База — паллеты или вес, по настройке организации. Показываются суммы до и после распределения. Остаток от округления относится на заказ с наибольшей долей.
- **Расходы парка.** Распределяются на рейс по дням или пробегу со ставкой из настроек. Результат показывается до и после распределения.
- **Маржа заказа** считается, когда у строк есть цена и себестоимость.
- **Доплаты.** Согласованный простой без счёта виден как задача на выставление.
- **Оплаты.** Платёж распределяется по счетам вручную; счёт может иметь несколько оплат. Нераспределённый платёж и платёж, подходящий к нескольким счетам, не закрывают счёт и попадают в «Разобрать».

Числовые примеры из PRD (выбор исполнителя при окне до 14:00 и сверка рейса с выручкой 112 000 ₽) становятся тестами модуля `domain`.

## 10. Импорт и экспорт

### 10.1. Импорт заказов

1. Загрузка файла, выбор листа и типа.
2. Сопоставление колонок; применение сохранённого шаблона.
3. Параметры шаблона: формат дат, часовой пояс (из точки или заданный), единицы измерения, суммы с НДС или без.
4. Проверка без записи: отчёт по строкам с ошибками.
5. Применение: итог «добавлено, обновлено, пропущено».

Обязательные поля: внешний номер заказа, точка (сохранённый идентификатор или название), окно, количество.

Правила:

- Ключ заказа — организация, шаблон как источник и внешний номер. Повторная загрузка обновляет запись и не создаёт дубль.
- Хеш файла хранится в задании; повтор того же файла сообщает об этом и показывает итог без изменений.
- Точка не найдена — ошибка строки; пользователь выбирает или создаёт точку и обрабатывает строку отдельно.
- Количество в файле меньше уже распределённого по рейсам — ошибка строки «конфликт с планом».
- Ошибочная строка исправляется в интерфейсе и обрабатывается отдельно от файла.

### 10.2. Очередь

Задания импорта лежат в таблице `import_job` и обрабатываются внутри процесса приложения по одному. Повторный запуск задания безопасен. Вебхуки следующих этапов встают в ту же очередь.

### 10.3. Экспорт

Выгрузки XLSX и CSV: заказы, рейсы, приёмка, план-факт, счета и оплаты. В каждой — внутренние и внешние номера, время, источник значения. Денежные колонки отсутствуют в выгрузке роли «склад».

## 12. Ссылка водителя

- Адрес `/d/<токен>`; токен — 32 случайных байта, в базе хранится хеш.
- Ссылка привязана к одному рейсу, имеет срок действия и отзывается логистом.
- Доступны только поля рейса из раздела 11; денежных полей нет.
- Отметки водителя пишутся в `trip_event` с источником «ссылка».
- Число запросов по токену ограничено.

## 13. Ошибки и защита данных

- Ключ 2ГИС хранится в переменной окружения сервера; в клиентский код, журналы и выгрузки не попадает.
- Все входные данные проверяются схемами zod на сервере.
- Одновременная правка рейса: запись с устаревшей версией отклоняется с сообщением.
- Каждое изменение рейса, плана, приёмки и денег пишется в `audit_log`.
- Ошибки доступа и формата показываются пользователю; неожиданные ошибки журналируются без персональных данных и ключей.

## 16. Запуск и демо-данные

- `docker compose up` поднимает приложение и базу; миграции применяются при старте.
- Команда наполнения создаёт демо-организацию: склад, распределительный центр с точкой въезда, получателей в пределах Новосибирска, машины, водителей, перевозчиков и файл заказов для импорта.
- Координаты демо-точек подобраны так, чтобы соседние точки были ближе 50 км.
- Настройки: `DATABASE_URL`, `ROUTING_MODE`, `TWOGIS_API_KEY`, `TWOGIS_KEY_EXPIRES_AT`, `TWOGIS_REQUEST_LIMIT`, `ROUTE_METRICS_STORAGE`, `EXPORT_PROVIDER_METRICS`, `MAP_TILE_URL`, `SESSION_SECRET`.
